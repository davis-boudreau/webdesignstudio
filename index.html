2. Brand Palette and Main Palette

Assign colours a purpose, then evaluate the combinations people will actually see.

How do I choose and check my palette?
Primary UI colour
Sets the anchor for your main action colour family. Choose a distinguishable emphasis colour; it does not need to fill every surface.
Supporting colour
Provides a quieter, related family for secondary emphasis. It is not automatically the page background or body-text colour.
Accent colour
Highlights selected content or actions. An accent does not automatically mean success, warning or error; those feedback roles have their own controls.
Ramp method
RGB mix moves toward white or black. OKLCH varies perceptual lightness and chroma. Both preserve your anchor at step 500; neither guarantees readable combinations.
Themes and contrast
Light and dark modes derive different semantic shades from the same anchors. Inspect text against its actual background, including hover and active states; add words or icons when colour communicates meaning.

    3. Build a readable type scale

    Establish comfortable body text first, then create a clear heading hierarchy.

    What do the typography controls change?
    Font family
    A font stack is an ordered set of fallbacks. System choices use installed fonts. Optional Google Fonts in the Typography studio load web fonts and show the matching HTML and CSS.
    Body size
    The base for the scale. Start with the 16 px example, then judge your content, audience and font. A slider value alone does not establish readability.
    Scale ratio
    Choose a named interval such as Minor Second or Major Third, or use a custom ratio. It multiplies each successive level: 16 px at the default Minor Third ratio (1.2) produces 19.2 px, 23.04 px and about 27.65 px. A larger ratio creates more dramatic size differences.
    Line height
    A unitless multiplier: 16 px text at 1.5 uses a 24 px line box. Give paragraphs breathing room without separating related lines too far.
    Letter spacing
    Heading and body spacing use em, so each adjustment scales with the text size. Check actual fonts and long labels; large negative values can crowd letters.
    Fluid headings
    The Typography studio lets you tune minimum/maximum viewports and the mobile heading percentage. Body and small text stay constant in this tool; larger headings use bounded fluid sizes.

    Use real headings, a paragraph and long labels. Check narrow widths, font fallbacks and 200% text resize; visual size is separate from an HTML heading's structural level.

    5. Design button variants and states

    Make an action easy to recognize, activate and understand before adding visual polish.

    Default state best practices: colour plus visible cues

    Keep the button recognizable across states. Communicate meaning with text or shape as well as colour.

    Hover
    Underline the label while retaining the button's shape and size.
    Keyboard focus
    Keep a visible outline. An underline supplements focus; it does not replace the outline.
    Active / pressed
    Use a momentary inset appearance. This is different from a persistent selection.
    Selected toggle
    Show a checkmark and ring. Keep the label unchanged between off/on and update aria-pressed="false" or "true" in application code.
    Loading
    Show “Processing…” and a progress indicator at full opacity. Respect reduced motion; announce progress/completion and prevent duplicate submissions in application code. aria-busy alone does not disable an action.
    Disabled
    Use native disabled behaviour and explain the reason in nearby text when needed. A faded colour alone is insufficient.

    These cues complement the contrast checks below. They do not repair unreadable text.

    W3C: use of colour · W3C: button behaviour · W3C: status messages.

    Variant and colour source
    Choose the variant you are editing. Palette sources follow their colour anchors; fixed swatches and custom colours remain specific choices. Manual background or text overrides take precedence over a source.

    3. Colour systems

    Each ramp has 11 steps. The centre step (500) preserves your chosen HEX value.

    RGB mix

    Interactive OKLCH colour wheel

    Explore hue around the wheel and chroma from centre to edge. Adjust perceptual lightness separately, then apply the colour to a palette anchor. Its ramp and theme roles update; step 500 preserves your chosen colour.

    Perceptual colour lab
    #004780

    The wheel shows an sRGB display approximation. At its edges, out-of-gamut chroma is reduced automatically. The ramp generator varies lightness toward its endpoints and gently reduces chroma at the extremes. The example swatches remain unchanged.

    How does OKLCH work, and how should I explore the wheel?

    OKLCH separates perceived lightness from colour intensity and hue. This makes it useful for exploring related colours without adjusting red, green and blue channels individually. Perceptual uniformity is an approximation, not a guarantee that every colour looks equally bright.

    • L — lightness: the lightness axis runs from black at 0% to white at 100%. Move the lightness slider to explore lighter or darker colours; it is separate from your position on the wheel.
    • C — chroma: move from the centre toward the edge to increase colour intensity. At zero chroma the colour is neutral, so changing hue has no visible effect. This tool's 0.4 limit is a control range, not a universal gamut boundary.
    • h — hue: move around the circle to change the colour family. Hue is an angle; 0° and 360° meet at the same point.
    • sRGB gamut: some combinations cannot be represented in sRGB. The tool reduces chroma for its HEX preview, so several vivid selections can look similar even though their requested OKLCH coordinates differ.

    Try this sequence:

    1. Choose Primary, Supporting or Accent. This loads that palette anchor into the wheel.
    2. Keep lightness steady and compare hues. Then lower chroma to create a quieter colour. Drag the wheel or use the labelled sliders with the keyboard.
    3. Adjust lightness and watch the HEX swatch and gamut message. The coordinates describe your requested selection; HEX shows the sRGB result.
    4. Select Apply to selected role to update the anchor and its ramp. Review the resulting text/background pairs in both themes.

    Exploring does not change the project until you apply. Load current role colour discards an uncommitted exploration and reloads the selected anchor; it does not restore the example defaults.

    Check contrast separately: OKLCH lightness is not WCAG relative luminance. Equal lightness values do not establish a passing contrast ratio, and a vivid colour does not automatically make a readable button.

    Read more: MDN: OKLCH syntax and colour coordinates. Then use Accessibility quick checks to inspect the generated colour pairs.

    Semantic colour roles

    How does the ramp generator work?
    • RGB Mix: interpolate each red, green and blue channel toward white for lighter steps, or black for darker steps. Round channels to whole numbers.
    • OKLCH: convert the anchor to perceptual lightness, chroma and hue; vary lightness and gently reduce chroma at the extremes; convert back to sRGB while reducing out-of-gamut chroma.
    • Neither method automatically guarantees contrast or an attractive palette. Review each role and theme.
    • Supporting and accent colours are independent anchors. Choose them for their purpose in the interface, then test the resulting combinations.
    Why use ramps and semantic colours?

    Ramps provide related shades for surfaces, text and interaction states. Step numbers are this tool's naming convention; step 500 is an anchor, not a contrast rating.

    • Lightness changes perceived brightness; chroma changes colour intensity; hue identifies the colour family.
    • A screen's gamut is its reproducible colour range. The wheel reduces chroma when converting an out-of-gamut selection to sRGB HEX.
    • Success, warning and error colours communicate meaning. Pair them with text or an icon, and check them in both themes.

    Try it: keep the anchor fixed, compare RGB mix with OKLCH, then inspect the text/background pairs in Accessibility quick checks.

    Named scale or mobile percentage: what is the difference?

    The type-scale ratio sets the interval between levels. Minor Second (1.067) creates small differences; Major Third (1.25) creates stronger hierarchy. Each level is the base size multiplied by the ratio raised to that level's step.

    The mobile heading percentage sets the minimum size of Display, H1 and H2 relative to their desktop maximum. At the default settings, a 39.06px H1 becomes about 32.03px at 82%. This changes the responsive endpoints, not the scale's name.

    Choose the hierarchy first, then reduce large headings only as much as your narrow layout needs. Reset responsive limits restores the viewport boundaries and percentage; it keeps your scale and letter-spacing choices.

    Why use REM for sizes and em for letter spacing?
    • PX reports a size in CSS pixels, not necessarily physical screen pixels. It makes specimen measurements easy to compare.
    • REM follows the root font size. With a 16px root, 24px is 1.5rem. The ladder uses this nominal conversion; a user's root font preference can change the rendered size.
    • em for letter spacing follows the element's own font size. At 0.02em, the extra spacing is 0.32px on 16px text and 0.64px on 32px text, so the spacing scales with the letters.
    • For font-size itself, em refers to the inherited parent size. REM avoids this nesting effect when defining a site-wide type scale.

    Positive letter spacing opens the text; negative values tighten it. Start near zero for body text and adjust headings cautiously. Font, language and size matter; spacing can disrupt scripts with connected letters. Test real content, zoom and user text-spacing overrides.

    Read more: MDN: CSS length units and letter spacing.

    Complete size ladder ? PX and REM

    REM values use a nominal 16px root: rem = px ? 16. The body-size control changes the scale base, not the root font size.

    Practice: document your type scale
    1. Create two frames: 375 px and 1280 px wide.
    2. Use the same font family and realistic content in both frames, in a design tool of your choice.
    3. Recreate the displayed sizes and line heights as named text styles.
    4. Compare hierarchy, wrapping, line lengths and readability.
    5. Record any changes before applying them to your integrated project.
    Why use a type scale and fluid sizes?

    A scale creates repeatable visual hierarchy: a 16 px base with the default Minor Third ratio (1.2) gives 19.2 px, 23.04 px and about 27.65 px steps. Choose sizes for real content, rather than using every step.

    • clamp(minimum, preferred, maximum) bounds a fluid size. Here the mobile multiplier affects Display, H1 and H2; body and small text stay constant.
    • rem follows the root font size. The calculation assumes a nominal 16 px root; viewport units alone do not follow a user's text-size preference.
    • Line height is a multiplier; ch approximates the width of the font's zero character. Both affect reading comfort and wrapping.

    Check: long headings, readable paragraphs, missing-font fallbacks and 200% text resize. A visual H1 size does not replace a meaningful HTML heading structure.

    Surface + border + feedback states
    
                  
    
                
    

              
    
                Why simulate states?
                
    
                  
    Simulations hold a temporary appearance still so you can compare states without keeping a pointer down or submitting a form. They make gaps in an interaction design easier to spot.
    
                  
      
                    
    • Hover means a pointer is over a control; focus identifies keyboard position; active is the moment of activation.
      • 
                    
    • Selected persists for a toggle. Disabled prevents use; read-only keeps a field available to inspect and copy.
      • 
                    
    • Invalid needs a useful correction message; loading needs progress feedback. Not every state applies to every component.
      • 
                  
    
                  
    Check: the tiles demonstrate styling. Separately test keyboard focus, actual validation, status announcements and repeat-click prevention in your implementation.
    
                  
    Read more: W3C: button interaction and accessible notifications.
    
                
    
              
    

              
    
            
    
              
    
              
    8. Accessibility quick checks
    
              
    

                
    
                  Review the defined text, swatch and component-state pairs in both themes. Required problems, conditional checks, potential uses and exemptions are labelled separately. Open Edit this colour to preview a change and its effects on related pairs before applying it.
                
    
                
    
                  Which contrasts need testing, and what is covered here?
                  
    
                    
      
                      
    1. Text and semantic roles: body/muted text on page, surface and muted surface; feedback colours as potential text; on-primary, on-secondary and on-accent against their action backgrounds.
      2. 
                      
    2. Boundaries and indicators: required control boundaries, status indicators and focus rings against adjacent surfaces. A decorative border or an action already identified by its text may not need a contrasting enclosing shape.
      3. 
                      
    3. Button Laboratory: every variant in default, hover, focus, active, selected, disabled and loading states; text, conditional boundaries, focus and selection rings. Transparent buttons are checked against each named host surface and the fixed theme-comparison background.
      4. 
                      
    4. General components and forms: all State Explorer states, including invalid, success and read-only; input borders, feedback outlines, general button hover and selected-tile indicators.
      5. 
                      
    5. Surfaces and opacity: card and nested-surface text composited over the stated parent surface. The same opacity can produce a different result on another background.
      6. 
                      
    6. Swatch candidates: all reference swatches and generated ramp steps paired with white and semantic text. These are potential uses, not failures of an unused colour.
      7. 
                    
    
                    
    Targets: 4.5:1 for normal text; 3:1 for qualifying large text and necessary non-text indicators. Text rows keep the 4.5:1 target and flag combinations suitable only for large text. Decisions use the unrounded ratio; composited samples show the nearest HEX colour.
    
                    
    Exemptions: genuinely inactive controls have no minimum contrast requirement. Read-only is not disabled. Loading remains subject to contrast unless the control is actually inactive; the Laboratory and Explorer demonstrate different loading treatments.
    
                    
    Still check manually: focus visibility, size and obscuring; whether a boundary is necessary; meaning without colour; real validation and announcements; placeholders, links, images, gradients, overlays and any combinations introduced in your finished site. The report models the named solid-colour contexts, not every browser-rendered pixel or possible state combination.
    
                    
    Reference: W3C text contrast, non-text contrast and meaning without colour.
    
                  
    
                
    
                
    
                  Edit theme colours: text, surfaces, borders and semantic roles
                  
    
                    
    Choose a theme and role, then preview a colour or a suggested alternative. Input boundaries use --control-border; decorative separators keep --border. Changing one does not have to change the other.
    
                    
    Overrides are saved in project JSON and used by previews, CSS exports and this report. They stay fixed when palette anchors change. Use generated colour removes the selected override.
    
                    
    
                      
    
                      
    
                    
    
                    
    
                    
    
                  
    
                
    
                
    
                  
    
                    
                    
                  
    
                  
    
                    
                    
                  
    
                  
    
                    
                    
                  
    
                  
    
                    
                    
                  
    
                
    
                
    
                
                
    
                
    
                  Also verify focus visibility, keyboard use, 200% text resize, content reflow, non-text contrast and meaning conveyed without colour.
                
    

              
    
                What does a contrast pass tell you?
                
    
                  
    The ratio compares a foreground with its background. A pass covers only the named pair, state, theme and context. Text and necessary non-text indicators have different targets; inactive exemptions and unused swatch candidates are labelled separately.
    
                  
      
                    
    • Text: aim for at least 4.5:1, or 3:1 for large text (at least 24 CSS px regular or about 18.67 CSS px bold). A heading label alone does not make text large.
      • 
                    
    • Controls: necessary visual boundaries and state indicators generally need 3:1 against adjacent colours. Check hover, focus and active colours separately.
      • 
                    
    • Context: transparency, images and gradients change the effective background. Colour alone must not carry an error, selection or status.
      • 
                  
    
                  
    Read more: W3C: text contrast and non-text contrast.
    
                
    
              
    

              
    
                What should I check beyond colour?
                
    
                  
      
                    
    • Use Tab and Shift+Tab: reach each interactive control in a useful order, see focus clearly, and avoid traps or focus hidden behind sticky content.
      • 
                    
    • Enlarge text to 200%. Check reflow at a 320 CSS px viewport and zoom the finished page; avoid clipped text and overlapping controls.
      • 
                    
    • Use descriptive headings, labels, links and error messages. Check screen-reader names, states and announcements; respect reduced-motion preferences.
      • 
                    
    • Test with realistic content and, where possible, people who use assistive technology. Automated checks and visual simulations cover only part of the experience.
      • 
                  
    
                  
    Use the W3C WCAG 2.2 quick reference to plan a fuller review.

    10. Design workflow
    
              
    

                
    Build a small system, test it with realistic content, then record the decisions someone else needs to use it.
    
                
      
                  
    1. Define: identify the audience, key tasks and content. Decide what the system needs to support.
      2. 
                  
    2. Choose: establish colour roles, typography and spacing. Record why each choice helps the audience.
      3. 
                  
    3. Apply: use those tokens in buttons, cards and forms; compare themes and responsive widths.
      4. 
                  
    4. Test: inspect contrast, keyboard interaction, text resizing, real content and component states.
      5. 
                  
    5. Deliver: export CSS and a JSON backup, document usage, and retest after integration.
      6. 
                
    

              
    
                Why document decisions as well as values?
                
    
                  
    A value says what to use; a short usage rule explains when to use it. Together they let another person make consistent changes.
    
                  
      
                    
    • Record the token or component, its purpose, allowed variants and one realistic example.
      • 
                    
    • For example: ?Use the primary button for the main action in a task; use a quieter variant for supporting actions.?
      • 
                    
    • Include testing evidence, known limits and a revision date. Keep exported CSS, JSON and usage notes together in version control or your shared project folder.
      • 
                  
    
                  
    Practice: ask someone else to build a small card or form using only your tokens and notes. Use their questions to improve the guidance.
